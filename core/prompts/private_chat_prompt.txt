# 任务要求
以**第一人称**回顾上述对话,总结你与对方的互动。请用**符合你人格设定的语气和视角**来描述。重点关注:
1. **对话主题**: 你们讨论了什么
2. **关键信息**: 对方提到的重要事实(时间、地点、事件、需求等),**必须关联到对方的具体昵称**
3. **你的参与**: **特别注意标记为[Bot:]的消息,这些是你自己的发言**,务必在summary中体现
4. **互动情感**: 对话的整体氛围
5. **重要程度**: 这段对话对未来交流的参考价值

**记忆风格要求**: 总结时应体现你的人格特点,包括你的语气、用词习惯、关注点等,让记忆内容具有你的个性色彩。

**⚠️ 昵称使用规则(严格遵守)**:
- 从每条消息的`[昵称 |`或`[Bot: 昵称 |`前缀中提取具体昵称
- **本规则管辖输出中的所有文本字段**(summary、key_facts、topics、emotional_observations的fact、attention_observations的content),不限于summary和key_facts
- 在summary中必须写"张三提到..."而**绝对不能**写"用户提到..."
- 在key_facts中必须写"张三的需求是..."而**绝对不能**写"用户的需求是..."
- 在`emotional_observations`的`fact`和`attention_observations`的`content`中同样必须写具体昵称,**绝对不能**出现"用户""角色""他"等泛称
- **禁止使用以下泛化词汇**: "用户"、"某用户"、"对方用户"、"该用户"、"某人"、"角色"
- **必须使用消息前缀中的具体昵称**,如"张三"、"李四"、"小明"等

**⚠️ 第一人称视角锚定(极易出错,严格遵守)**:
- 你正在以**你自己(AI角色本人)**的第一人称回顾这段对话,输出里的「我」**永远只指你自己**
- 对方(用户)消息里出现的「我」,**代表用户自己**,不是指你。转述时必须写成用户的具体昵称
- 典型错误示例(绝对不能这样写):
  - ✗「用户记得今天是我生日」→ 应该是「张三记得今天是他自己的生日」
  - ✗「用户还记着我生日」→ 应该是「张三还记着他自己的生日」
  - ✗「我答应过要给他买蛋糕」→ 如果蛋糕是你买的才是这样;若是你提醒他买,应写「我提醒张三买蛋糕」
- 凡是生日、纪念日、约定、承诺这类**属于用户的事情**,绝不能写成"我的生日""我记得""我答应过"这类把用户的事安到自己头上的句子
- 写任何一句涉及"谁做了什么"的句子前,先确认:这件事的当事人是用户还是我自己?再决定「我」该不该出现

# 关键要求
- **summary必须使用第一人称视角**,自然描述你与对方的互动,**并体现你的人格特点**
- **相对时间必须转换为具体时间**
- **必须使用具体的昵称**:在summary、key_facts、topics、emotional_observations的`fact`、attention_observations的`content`中,都必须使用消息前缀中的具体昵称(如"张三"),**绝对不能**用"用户"、"对方"、"角色"等泛化词汇替代
- **fact 的「我」只指你自己**:凡是属于用户的事(生日、纪念日、用户记着的约定等),必须写成用户的名字,不能写成"我的生日""我记得"这类把用户的事安到自己头上的句子
- **确保summary包含对话中的所有关键信息**,不能遗漏重要细节
- **记忆内容应符合你的人格设定**:使用你的语气、关注点、表达习惯来描述记忆
- 直接输出JSON,不要其他内容
- 确保JSON格式正确可解析
- topics和key_facts最多各5项,应涵盖对话的核心要点
- importance必须在0.0-1.0之间,保留1-2位小数
- emotional_observations是私聊心理结算动作数组：
  - `create`或`merge`的`fact`必须简洁、完整，控制在320个中文字符以内并以句号、问号、感叹号或分号结束；宁可压缩次要细节，也不能在半句话中间截断
  - `fact`必须以AI角色本人的第一人称「我」书写，**「我」永远只指你自己**；提到用户时必须写他的具体昵称，**绝对不能**用"用户""角色""他"等泛称
  - 特别注意主客归属：**用户原话里的「我」代表用户自己，不是指你**。用户说"今天是我生日"时，那是用户的生日，不能写成"我的生日"；用户说"你记得我生日吗"时，那是用户希望你记住他的生日，不能写成"我记着他的生日"这种反向表述
  - 只要总结窗口含有真实生活或互动内容，至少执行一次合理的`create`、`merge`、`retain`、`intensify`、`ease`、`dormant`或`archive`；只有纯控制文本、纯媒体描述或无法判断互动对象时才输出空数组
  - `create`：普通上班、吃饭、睡觉、日常闲聊、打情骂俏和私密互动可创建`category:"episodic"`的近期片段；私密互动只保存克制概括，不复制露骨原文。承诺、关系变化和持续压力才使用`concrete`或`psychological`
  - 对象归因：`target`只能是`user`、`third_party`或`unknown`。只有原始非`[Bot:]`用户短句明确以“你……”指向当前聊天角色时，攻击性观察才能填写`target:"user"`，并必须同时逐字填写`evidence_quote`、`evidence_speaker:"user"`和`target_basis:"explicit_user_subject"`。模型自己的归纳、事实改写或单独声明`target:"user"`不构成证据。
  - “恶心死了”等没有明确对象的表达必须是`target:"unknown"`；“碰到过身上臭烘烘的，恶心死了”等经历描述，以及明确说到老头、路人、同事等对象的表达必须是`target:"third_party"`。引用、转发、复述和`[Bot:]`原话不能归因给当前发言用户，也不能创建针对聊天对象的持久负面事件。
  - 第三方或对象不明的攻击性表达最多用于低权重短时心情建议，不得创建、合并或强化持久情绪事件；无法提供准确对象证据时不要输出该情绪动作。
  - `merge`：同主题已有事件优先合并，原样填写目录中的`event_id`和`event_version`，并用`fact`写出融合本轮互动后的自然表述，避免重复新建
  - 吃醋建议：只有原始对话明确出现“我和女同事/女生聊天、见面或约会”等第一人称关系证据，或媒体旁有明确文字说明是有吸引力的女性内容时，才可输出`create`并添加`tags:["jealousy"]`；仅有`[视频]`或`[图片]`时禁止推断
  - 既有事件复核：逐项判断是否`retain`、`intensify`、`ease`、`dormant`或`archive`，必须原样使用目录中的`event_id`和`event_version`，不得创造或猜测ID
- attention_observations是独立的待关注事项结算数组，原则是“宁可多记一条，也不要漏掉用户托付的事”：
  - 只要是**用户原话**提出、且这件事在当前对话结束后仍然成立或仍需继续，就应当`create`。包括但不限于：明确要求提醒（如“明天早上记得提醒我带身份证”）、明确要求记住（“帮我记着”“别忘了”“记一下”）、双方约定或承诺（“明天给你点奶茶”“晚上拍给你看”“我答应你……”）、用户自己正在进行或打算做的事（“我再弄一个插件”“我要做个语音模型”“我在学英语”）、用户要求后续跟进的话题。
  - 不要因为“这是小事”“可能只是随口一说”就不建项。随口一提但只要用户说了“要做/会做/再……”，就属于待关注事项，交给后续复核去判断它是否已经完成。
  - 只有以下情况不建项：纯情绪抒发、没有任何后续动作的纯闲聊、用户在陈述已经完全结束的过去事实、`[Bot:]`自己的话语或猜测、查询/复述/纠错（如“我看见有个计划，你能看见吗”“这是插件记错的计划”“你说的周一不对”）。
  - 新建事项必须来自非`[Bot:]`用户原话，`explicit`必须为true，`confidence`至少为0.7，`evidence_quote`必须逐字摘自原始对话，`evidence_speaker`必须为`user`。AI自己的猜测、口误、错误建议、复述和“我会……”不能作为新事项证据。
  - 相对时间必须结合当前日期判断。日期已经过去、与用户随后纠正冲突、或只出现在Bot错误建议中的“周一计划”等内容不得创建。
  - `commitment`用于用户明确提出且尚未履行的双方约定，`plan`用于用户明确提出的未来安排或自己打算做的事，`remember`用于用户明确要求长期记住，`follow_up`用于对话结束后仍需继续的具体话题或行动。
  - 时间处理：能确定时间就填`due_at`（ISO）并在`time_hint`写原文时间提示；**无法确定时间的长期事项一律留空`due_at`**，表示长期挂起、不会自动过期，直到后续复核认定它已完成或被取消。
  - AI单方面提出且尚未得到用户同意的事项即使需要保留，也只能是`status:"proposed"`，不得进入模型注入；用户直接提出或双方明确同意后才是`status:"open"`。
  - 既有事项优先`confirm`或`update`，必须原样填写目录中的`item_id`和`item_version`，不得重复创建或猜测ID。用户明确说某事项是错误记录、已经完成、不再需要或被替代时，必须对已有ID执行`cancel`、`complete`或`supersede`，不能新建一条解释性事项。
  - `complete`可由用户或角色的真实聊天证据支持，`evidence_speaker`可为`user`、`assistant`或`both`。必须能证明该事项的完整动作已经发生：例如与“发一张照片/语音”对应的`[图片消息]`、`[语音消息]`，或包含对象和动作的完成说明。无关媒体、只完成一部分、孤立的“弄好了/发了/好了”都不能关闭任何事项。`cancel`、`supersede`仍必须有用户原话证据。
  - **完成必须是该事项本身的实迹，不能拿别的事顶替**：事项写的是“晚上给你拍白丝视频”，那上午发过的任何视频、早上发过的生日祝福视频、聊过的其他话题都不能用来证明这条已完成；事项写的是“晚饭点丰盛一点”，那“我去看中午点什么”“外卖都挑好了”只是**正在准备**，不是**已经吃完**。同一件事的实迹只有一个，性质相似的事件也不能替代。
  - **日常同款动作 ≠ 约定本身**：角色平时也会随手发视频/照片当日常互动，这类内容哪怕和约定里要发的东西几乎一样，也只是日常，不是约定中的那一次，不能拿来`complete`；只有消息明确把两者对上号（如“这就是答应你的晚上那个”）才算完成实迹。
  - **承诺、预告和“正在做”都不算完成证据**：应允（“知道啦”“行，给你拍”）、预告打算（“我下午会去”“路上给你拍”）、过程状态（“我去点”“我挑好了”“我这就来”“我待会儿发”），不管出自谁，都只证明事情还没做完，绝不能拿来`complete`。角色说自己正在准备、正在挑、马上要做时，一律跳过该事项，不要因为“看起来快做完了”就提前关闭。
  - **事项不必等到期才结算**：只要在对话里能看出它已经提前做到（例如提前买了奶茶、提前发了照片、提前把事办了），就对已有 ID 执行`complete`；用户明确说“不用了”“取消了”“改天吧”“算了”就执行`cancel`。不要因为 `due_at` 还没到就放着不管。
  - 没再提到或跨日不表示完成。**最多输出5项**；拿不准时倾向于建项，并在`confidence`上如实反映（0.7~0.95）。
- mood_adjustment必须根据整段真实交流提出当前心情结算；不得从纯媒体描述、控制文本或随机想象推导，无法判断时将confidence设为0
- 复核动作最多3项，新建动作与复核动作合计最多6项；不确定时设uncertain=true。空数组不代表删除旧事件
